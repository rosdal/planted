# v0.3 performance: gate 1

Gate 1 from the [design doc](../design.md): 10 users drawing at 60 fps, no lost strokes, undo only undoes your own work. Procedure from [the v0.3 todo](../todo/v0.3.md), sections 7 and 8.

**Status: not yet passed.** Correctness holds in every run. Frame rate holds for most of every run, but the machine used so far was shared with other heavy work, and the last fix (stroke tiles) still needs a clean 5-minute run. The final run belongs on the desktop below.

## How to run it

```sh
pnpm db:up
# API on 5198, production web build on 5199 (CORS origin must match the web port)
SERVER_PORT=5198 WEB_ORIGIN=http://localhost:5199 pnpm --filter @planted/server exec tsx src/main.ts
VITE_API_URL=http://localhost:5198 pnpm --filter @planted/web build
pnpm --filter @planted/web exec vite preview --port 5199 --strictPort

pnpm --filter @planted/scripts gate1 --minutes 5 --seed 2000 --trace ./trace-v0.3.json
pnpm --filter @planted/scripts gate1 --minutes 1 --throttle 4      # stretch: 4× CPU throttling
```

`scripts/gate1.ts` opens two real Chrome windows ("Human A" at 1920×1080, measured; "Human B" at 1280×800), starts 8 drawing bots, and samples the board's overlay every 5 s. Human A never stops: stroke, middle-drag pan, wheel zoom in and out, sometimes `0` to fit. It then checks convergence, records a 30 s trace as a separate phase, writes 2,000 more strokes, and pans for 15 s at fit and at 8×. The overlay (F3, or `?perf=1` in production builds) shows the same numbers live.

The scripted humans are harder on the board than people (no pauses), but they can't judge "feels laggy". Gate items 3 and 4 need a person.

## Results

### Correctness: passes

| Run | Objects at end | Bot strokes − undos | Human A      | Human B (net) | Doc hashes                        |
| --- | -------------- | ------------------- | ------------ | ------------- | --------------------------------- |
| 1   | 555            | 387                 | 89           | 79            | all `6c3b2b23` (2 pages + 8 bots) |
| 2   | 569            | 390                 | not recorded | not recorded  | all `1a6f1021`                    |
| 3   | 508            | 378                 | 63           | 67            | all `91b347a9`                    |

Every stroke is accounted for (objects = bot strokes − undos + Human A + Human B), and every client ends on the same doc hash. The E2E test checks that undo removes only your own stroke, on both clients.

### Frame rate during the 5-minute run: mostly 60 fps, with stalls

Clean run (run 2, before the tile change): 52 of 60 samples were 58–60 fps with 0–1% dropped frames. The other 8 fell in four short windows (~16 s, 101–106 s, 136–141 s and 176–196 s), down to 24 fps.

Run 3 started the same way, then degraded once the `patchd` scan began. Long-animation-frame data from that run shows what the stalls are made of. In the slow windows, script time is **0–4%** of the long frames. The board's own JavaScript isn't the cost; the main thread is waiting on rendering, the GPU process, or a busy machine. The 30 s trace agrees: renderer main thread busy 20% (Pixi's whole tick ~2.4 ms a frame), **GPU process main thread busy 81%**.

About p95: on a 60 Hz display `ticker.deltaMS` jitters around 16.67 ms, so p95 sits at 17.0–17.1 ms even with no dropped frames. The gate's "p95 ≤ 16.7 ms" can't be met literally with this measure. The overlay also reports **dropped frames** (frames over 1.5× the median) as a share of the last 5 s. Read gate item 1 as "dropped ≈ 0% and no frame over 50 ms".

### 2,000+ strokes on screen (gate item 6)

| Case                                    | fps | p95     | Longest  | Notes                                                                 |
| --------------------------------------- | --- | ------- | -------- | --------------------------------------------------------------------- |
| 2,600 strokes, one window, pan at fit   | 60  | 17.0 ms | 17–50 ms | Before tiles; renderer 56% CPU, GPU process 70–80%                    |
| Same, `world` as a render group         | 60  | 17.1 ms | 33 ms    | Renderer 37–39%, GPU process 65–67%                                   |
| 2,543 strokes, gate harness, pan at fit | 35  | 33.6 ms | 100 ms   | Human B's window also open on the same GPU; now closed for this phase |
| 2,543 strokes, pan at 8×                | 60  | 17.0 ms | 17.9 ms  | Culling leaves a few tiles on screen                                  |

A 30-point stroke tessellates to ~584 vertices with round caps and joins, so 2,600 strokes is ~1.5 M vertices. Fixes that went in:
- **`world` and the live layer are render groups**, so a pan moves a GPU transform instead of re-transforming every vertex.
- **Strokes sit in 8 × 8 spatial tiles**, each its own render group. A commit rebuilds only the ~40 strokes in its tile, and the culler tests 64 tile bounds instead of every stroke.

The fit-pan case with tiles still needs measuring on a quiet machine. If it still drops, the next steps are bevel joins (~40% fewer vertices, nearly invisible on dense strokes), then fewer curve subdivisions.

At 8× the stroke curves show slight faceting from the quadratic subdivision. Check by eye whether it's acceptable.

### Fixes found by measuring

- **React re-rendered the board page on every remote cursor move**: `usePeers` returned a new list on every awareness change, ~270 renders a second with 9 peers. It now changes only when someone joins, leaves, or renames. Before the fix, 8 bots joining cost a 33–81 ms frame; after, none over 18 ms.
- **Harness artefacts, not board problems:**
  - Chrome throttles occluded windows, which took Human A down to a few fps while Human B's window covered it; the harness now disables that.
  - A 30 s trace with the default categories was 400 MB and stalled the whole machine; tracing is now a lighter, separate phase.

### Not measured yet

- The clean 5-minute run after the tile change (gate items 1 and 6)
- Stretch: 4× CPU throttling (`--throttle 4`)
- Gate items 3 and 4 by hand: own strokes under the pointer with no lag; remote strokes grow and don't flicker on commit; cursors smooth through pan and zoom; a closed tab's cursor gone within 1 s. The server drops a socket's awareness on close, so the last should hold.

## Other findings

- **Bundle:** the board route loads ~400 KB gzip of JS (Pixi is most of it), over the design doc's 300 KB first-load budget. The landing page is unaffected (route code splitting). Worth a look when 0.7 sets real budgets; Pixi's renderer and extension imports can be trimmed.
- **Server:** with 8 drawing bots the relay sits at 15–20% of one core, 130–140 MB RSS, and p95 update fan-out of 4–7 ms when the machine is quiet.
