# v0.5 performance: first board paint

Done check 7 from [the v0.5 todo](../todo/v0.5.md): floor SVGs under the size budget, and the first board paint on a cold cache under 2.5 s on 4G.

**Status: passes on Fast 4G (1.76 s median), fails on Lighthouse's slow-4G profile (4.05 s median).** The content is not the problem. A floor SVG is under 1 KB gzipped, and a whole map (manifest, map.json, first floor) is a few KB. About 500 KB crosses the wire per cold load, and nearly all of it is the app: ~220 KB of gzipped JS (Pixi is most of it) plus the web fonts. On a 1.6 Mbps link that alone takes about 2.5 s. Getting under 2.5 s there means splitting or shrinking the board bundle, which is a job for 0.6 or later.

Measured 2026-10-26 on commit `403af31`, desktop (Windows 11, Chrome via Playwright, headless).

| Profile                                                             | Runs | Median | Max    | Transferred |
| ------------------------------------------------------------------- | ---- | ------ | ------ | ----------- |
| Fast 4G: 60 ms RTT, 9 Mbps down, 1.5 Mbps up                        | 5    | 1.76 s | 1.81 s | 500 KB      |
| Slow 4G (Lighthouse mobile): 150 ms RTT, 1.6 Mbps down, 750 kbps up | 5    | 4.05 s | 4.09 s | 500 KB      |

The spread between runs was about 0.1 s, so both verdicts are well clear of the noise. These are lab numbers on one machine with the API on localhost, so real users add server latency on top.

**Floor size budget:** the largest floor is `practice-depot/1f.svg` at 0.5 KB gzipped, against a 150 KB budget that `pnpm content:build` enforces. Hand-drawn real maps will be much larger; the budget catches them at build time.

## What is measured

The time from navigation start to two animation frames after the first floor's SVG has finished loading and the board exists. By then the floor is parsed into Pixi geometry and drawn. Each run uses a fresh browser context, so the HTTP cache is empty. The room is created before the run, and the page loads it from its share link.

## How to run it

```sh
pnpm db:up
pnpm content:build && pnpm content:serve                  # content on 5174
pnpm --filter @planted/server dev                         # API on 3000, CORS for 5173
VITE_API_URL=http://localhost:3000 VITE_CONTENT_URL=http://localhost:5174 pnpm --filter @planted/web build
pnpm --filter @planted/web exec vite preview              # production build on 5173
```

Then open a room's edit link with `?perf=1` in Chrome DevTools, set network throttling, disable the cache and reload. The numbers above came from a Playwright script doing the same thing with CDP network emulation five times per profile. The script isn't committed; it is about 60 lines, and 0.7's visual-regression work is the natural place for a reusable version.
